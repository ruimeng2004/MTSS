# 平衡簇识别与分析报告

**分析日期**: 2026-01-17  
**分析目标**: 识别任务建模平衡的 bug 簇，探索"both"策略的可行性

---

## 1. 背景与动机

### 1.1 问题描述

在 BTMS 实验中，我们通过聚类方法为每个 bug 选择最优的任务建模方式（edit 或 gen）。然而，某些 bug 可能在两种任务建模下表现相近，强制选择其中一种可能不是最优策略。

### 1.2 研究问题

- **RQ1**: 有多少 bug 在 edit 和 gen 任务建模下 PPL 差距很小？
- **RQ2**: 这些"平衡"的 bug 是否会聚集在同一个簇中？
- **RQ3**: 能否通过簇的特征识别出这些平衡簇，并为其采用"both"策略？

### 1.3 "Both"策略定义

对于平衡簇中的 bug，不强制选择 edit 或 gen，而是：
- 同时使用两种任务建模
- 或者标记为"任意皆可"
- 目标是避免错误的强制选择，提升整体 Win Rate

---

## 2. 分析方法

### 2.1 PPL 差距定义

对于每个 bug，定义其 PPL 相对差距为：

```
gap = |PPL_edit - PPL_gen| / min(PPL_edit, PPL_gen) × 100%
```

- gap < 10%: 差距很小，两种建模几乎等价
- gap < 20%: 差距较小，两种建模都可接受
- gap < 30%: 差距中等，有一定偏好但不强烈

### 2.2 平衡簇识别标准

一个簇被识别为"平衡簇"需要满足：

```
簇内 gap < threshold 的 bug 数量 / 簇大小 ≥ proportion_threshold
```

**参数设置**:
- `gap_threshold`: PPL 差距阈值（10%, 20%, 30%）
- `proportion_threshold`: 最小占比（50%, 70%）

**解释**: 如果一个簇中至少 50%（或 70%）的 bug 的 PPL 差距小于阈值，则认为这是一个平衡簇。

### 3.2 K 值影响分析

#### 3.2.1 趋势观察

两个模型都显示出相同的趋势：
- **K 值越大，识别出的平衡 bug 越多**
- K=50 时：qwen3_coder 0.6%, qwen3_30b 1.4%
- K=500 时：qwen3_coder 8.7%, qwen3_30b 14.5%
- **增长倍数**: 约 10 倍

#### 3.2.2 原因分析

1. **簇粒度更细**: K 值大时，每个簇更小、更同质化
2. **单点簇增多**: 小簇更容易满足"占比 ≥ 50%"的条件
3. **噪声捕获**: 大 K 值可能将个别异常点单独成簇

- qwen3_30b 识别出更多平衡 bug

## 6. 关键发现

### 6.1 单点簇主导

**发现**: 70-80% 的平衡簇是单点簇（size=1）

**影响**:
- 单点簇不需要聚类就能识别（直接计算每个 bug 的 PPL 差距）
- 聚类的价值主要在于识别多成员平衡簇
- 但多成员平衡簇数量有限（10-22 个）

**建议**: 
- 可以采用混合策略：
  1. 直接计算所有 bug 的 PPL 差距
  2. 对差距小的 bug 直接应用"both"策略
  3. 不需要依赖聚类

### 6.2 多成员平衡簇稀少

**统计**（K=500, 20%, 50%）:
- qwen3_coder: 10 个多成员簇，最大 4 成员
- qwen3_30b: 22 个多成员簇，最大 3 成员

**原因分析**:
1. **任务建模差异明显**: 大多数 bug 在 edit 和 gen 下表现差异显著
2. **聚类基于相似性**: 相似的 bug 不一定都是平衡的
3. **数据集特性**: Defects4J 的 bug 可能本身就有明确的任务偏好

### 6.3 模型差异显著

qwen3_30b 识别出的平衡 bug 是 qwen3_coder 的 1.66 倍

**可能原因**:
1. **模型能力**: qwen3_30b 在两种任务上的能力更均衡
2. **PPL 分布**: qwen3_30b 的 PPL 差距整体更小
3. **聚类质量**: 不同 view 和算法导致的差异

**建议**: 需要进一步分析两个模型的 PPL 分布特征

## 7. "Both"策略可行性评估

### 7.1 潜在收益

假设对平衡 bug 应用"both"策略：

#### 7.1.1 理论上界

如果所有平衡 bug 都能通过"both"策略获得正确决策：

- **qwen3_coder**: 最多提升 8.7% 的 bugs 的决策正确率
- **qwen3_30b**: 最多提升 14.5% 的 bugs 的决策正确率

#### 7.1.2 实际预期

考虑到：
1. 并非所有平衡 bug 在当前策略下都是错误的
2. "both"策略可能带来额外成本（需要运行两次）

**保守估计**: Win Rate 提升 2-5 个百分点

### 7.2 实施成本

#### 7.2.1 计算成本

对于平衡 bug，需要：
- 运行两次任务建模（edit + gen）
- 额外计算成本：8.7% - 14.5% 的 bugs × 2 = 17.4% - 29% 的额外推理

#### 7.2.2 复杂度成本

- 需要修改决策逻辑
- 需要处理两个输出结果
- 可能需要额外的合并或选择机制

### 7.3 可行性结论

✓ **可行，但收益有限**

**理由**:
1. 覆盖率较低（8.7% - 14.5%）
2. 大部分是单点簇，不需要聚类
3. 计算成本增加 17-29%

**建议**:
- 优先实施简化版本：直接基于 PPL 差距判断，不依赖聚类
- 先在小规模数据上验证实际 Win Rate 提升
- 如果提升显著（>3%），再考虑全面部署

## 8. 替代方案探索

### 8.1 方案 A：直接 PPL 差距判断

**方法**: 
```python
for bug in bugs:
    gap = calculate_ppl_gap(bug)
    if gap < 20%:
        strategy = "both"
    else:
        strategy = "edit" if ppl_edit < ppl_gen else "gen"
```

**优点**:
- 简单直接，不需要聚类
- 覆盖率与聚类方法相当
- 计算成本低

**缺点**:
- 无法利用簇的集体信息
- 可能对个别异常点敏感

### 8.2 方案 B：加权投票

**方法**: 
```python
for cluster in clusters:
    if is_balanced_cluster(cluster):
        # 对平衡簇使用加权投票
        weight_edit = 1.0 / avg_ppl_edit
        weight_gen = 1.0 / avg_ppl_gen
        if abs(weight_edit - weight_gen) < threshold:
            strategy = "both"
```

**优点**:
- 利用簇的集体信息
- 对噪声更鲁棒

**缺点**:
- 实现复杂
- 多成员平衡簇太少，优势不明显

### 8.3 方案 C：自适应阈值

**方法**: 
```python
# 根据簇的大小和纯度动态调整阈值
for cluster in clusters:
    threshold = base_threshold * (1 + cluster_purity)
    if cluster_gap < threshold:
        strategy = "both"
```

**优点**:
- 更灵活，适应不同簇的特征
- 可能提高识别精度

**缺点**:
- 需要额外的参数调优
- 增加系统复杂度

## 9. 结论与建议

### 9.1 主要结论

1. **平衡 bug 存在但数量有限**: 8.7% - 14.5% 的 bugs 在两种任务建模下表现相近

2. **单点簇主导**: 70-80% 的平衡簇是单点簇，聚类的价值有限

3. **K 值影响显著**: K=500 时识别效果最好，但也带来更多单点簇

4. **模型差异明显**: qwen3_30b 比 qwen3_coder 识别出更多平衡 bug

5. **阈值权衡**: 推荐使用 gap < 20%, proportion ≥ 50% 作为平衡标准

### 9.2 实施建议

#### 9.2.1 短期（立即可行）

✓ **实施方案 A：直接 PPL 差距判断**

```python
# 伪代码
for bug in bugs:
    ppl_edit = get_ppl(bug, "edit")
    ppl_gen = get_ppl(bug, "gen")
    gap = abs(ppl_edit - ppl_gen) / min(ppl_edit, ppl_gen)
    
    if gap < 0.20:  # 20% threshold
        apply_both_strategy(bug)
    else:
        apply_best_strategy(bug)
```

**预期收益**: Win Rate 提升 2-5 个百分点

#### 9.2.2 中期（需要验证）

1. **A/B 测试**: 在部分数据上对比"both"策略与当前策略的实际效果
2. **成本分析**: 评估额外计算成本是否值得
3. **阈值优化**: 基于实际结果调整 gap threshold

#### 9.2.3 长期（研究方向）

1. **理解平衡 bug 的特征**: 为什么这些 bug 在两种建模下表现相近？
2. **改进任务建模**: 是否可以设计更好的任务表示，减少平衡 bug 的数量？
3. **多任务学习**: 训练一个同时擅长 edit 和 gen 的模型

### 9.3 不建议的方向

✗ **不建议**: 依赖聚类来识别平衡簇
- 原因：单点簇主导，聚类价值有限
- 替代：直接基于 PPL 差距判断

✗ **不建议**: 使用过于激进的阈值（如 30%, 50%）
- 原因：可能包含非真正平衡的 bug，降低精度
- 替代：使用保守或平衡的阈值
