# Bug Task Model Selection 实验报告

## 1. 项目目标

给定一个 bug，预测应该使用 **edit**（编辑式）还是 **gen**（生成式）任务建模来修复。

**核心思路：**
1. 用 bug 的不同视图（view）生成 embedding
2. 对 embedding 进行聚类
3. 每个 cluster 选代表，用代表的 PPL 决定整个 cluster 的策略
4. 新 bug 来了，找到它属于哪个 cluster，使用该 cluster 的策略

---

## 2. 数据概况

### 2.1 Bug 数据
- **总数**: 698 个 bug（来自 Defects4J）
- **视图类型**: 7 种
  - report: bug 报告
  - test: 测试代码
  - error: 错误信息
  - error_plus_test: 错误信息 + 测试代码
  - buggy_code: 有 bug 的代码
  - buggy_code_obfuscated: 混淆后的 buggy 代码（标识符 hash 化）
  - buggy_code_mixed: buggy 代码 + 头部注释

### 2.2 PPL 数据
- **模型**: 2 个
  - qwen3_coder
  - qwen3_30b
- **任务建模**: 2 种
  - edit: 编辑式
  - gen: 生成式
- **实验配置**: 4 种组合
  - qwen3_coder_edit, qwen3_coder_gen
  - qwen3_30b_edit, qwen3_30b_gen

### 2.3 Baseline（最佳单一策略）
| 模型 | always_edit | always_gen | 最佳策略 |
|------|-------------|------------|----------|
| qwen3_coder | 44.4% | **55.6%** | gen |
| qwen3_30b | **52.3%** | 47.7% | edit |

---

## 3. 实验过程

### 3.1 初始实验：全量聚类（错误方法）

**问题**: 最初将 4886 个 item（698 slug × 7 view）一起聚类，但 PPL 是 slug 级别的，导致评估不正确。

**修正**: 改为按 view 分别聚类，每个 view 698 个 item。

---

### 3.2 Per-View 实验（k=20）

对每个 view 单独聚类（k=20），评估路由效果。

**qwen3_30b (baseline: edit 52.3%)**
| View | Routed Win Rate | vs Baseline |
|------|-----------------|-------------|
| report | 52.6% | +0.3% |
| error | 48.9% | -3.4% |
| buggy_code_obfuscated | 48.9% | -3.4% |

**发现**:
- qwen3_coder: buggy_code 类 view 效果最好

- 两个模型对 view 的敏感度完全不同

---

### 3.3 Cluster 内部一致性分析

分析 k=20 时，每个 cluster 内部的 edit/gen 偏好是否一致。

**结果（buggy_code_mixed, qwen3_coder）**:
- 路由正确的 cluster: 18/20 (90%)
- 但 cluster 内部一致性普遍只有 50-60%
- 即使选对了多数派，还有 40-50% 的成员被"误伤"

**结论**: 代表选择是准的，但 cluster 太粗，内部分裂严重。

#### 3.7.3 Win Rate vs 路由准确率的差距分析

以 buggy_code_mixed + qwen3_coder + k=20 为例：
- Cluster 级别路由准确率: **90%** (18/20 个 cluster 选对了多数派)
- Slug 级别 Win Rate: **57.4%** (401/698 个 slug 被正确路由)

**差距来源：**
- 在选对的 cluster 中被误伤的 slug (少数派): **259 个**
- 在选错的 cluster 中被误伤的 slug (多数派): **38 个**
- 总误伤: **297 个 slug**

**结论：** 路由准确率高 ≠ Win Rate 高。问题不在于"选错"，而在于 cluster 内部本身就很分裂（很多是 51% vs 49%），即使选对了多数派，还有大量少数派被误伤。

## 4. 关键发现

### 4.1 K 值影响
- k 越大，路由效果越好
- k=500 时胜率达 87-89%，但此时平均每个 cluster 只有 1.4 个 bug
- **没有明显拐点**，说明聚类粒度越细越好

### 4.2 View 影响
- **qwen3_coder**: buggy_code 类 view 在小 k 时就有正向提升
- **qwen3_30b**: 需要 k≥50 才开始有正向提升，buggy_code_obfuscated 表现最稳定

### 4.3 核心问题
- 698 个 bug 分成 150+ 个 cluster，平均每个 cluster 只有 4-5 个 bug
- 这基本上没有"聚类"的意义，几乎是在记忆每个 bug 的特性
- **embedding 相似性 ≠ 任务建模偏好相似性**

---

## 5. 结论与建议

### 5.1 当前方法的局限
- 聚类方法在小 k 时效果有限（+1-5%）
- 大 k 时效果好，但失去了泛化能力
- embedding 可能没有捕捉到与 edit/gen 偏好相关的信息

### 5.2 可能的改进方向

1. **直接分类器**: 用 embedding 作为特征，训练二分类器预测 edit/gen
2. **换特征**: 提取手工特征（代码行数、修改范围、错误类型等）
3. **换 embedding**: 试试代码专用的 embedding（CodeBERT、UniXcoder）
4. **分析规律**: 先做 EDA，看 edit/gen 偏好有没有明显模式

### 5.3 推荐下一步
用 5-fold 交叉验证 + 随机森林/SVM，直接用 embedding 预测 edit/gen，看能达到多少准确率。如果比 baseline 高不了多少，说明 embedding 本身就不适合这个任务。
