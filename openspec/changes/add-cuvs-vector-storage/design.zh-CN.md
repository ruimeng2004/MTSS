## 背景

嵌入模块当前生成文本嵌入并将其存储为 JSON 文件。虽然足以用于初期原型开发，但这种方法存在局限性：

1. **性能瓶颈：** 对于超过 10K 向量，在 Python/NumPy 中加载大型 JSON 文件并计算相似性搜索速度缓慢
2. **内存效率低：** 所有向量必须加载到内存中进行相似性操作
3. **无索引：** 最近邻查询的线性搜索 O(n) 复杂度
4. **聚类准备：** 层次聚类需要高效的距离矩阵计算和增量更新

cuVS（CUDA Vector Search）解决了这些问题：
- GPU 加速的近似最近邻（ANN）搜索
- 多种索引类型（IVF-Flat、IVF-PQ、CAGRA），具有不同的速度/精度权衡
- 基于 RAPIDS 生态系统构建（与 cuML 的 GPU 加速聚类互操作）
- 索引的持久磁盘存储

**利益相关者：**
- 分析嵌入相似性模式的研究人员
- 未来的聚类和可视化功能
- 对性能敏感的批处理工作流

## 目标 / 非目标

### 目标
- 使用 cuVS 启用 GPU 加速的向量存储和检索
- 提供与现有 `TextEmbedder` 工作流的无缝集成
- 支持具有可配置参数的多种索引类型
- 保持向后兼容性（JSON 导出仍然可用）
- 为 cuVS 存储向量上的层次聚类奠定基础
- 允许将现有 JSON 嵌入迁移到 cuVS

### 非目标
- 实现完整的层次聚类算法（单独的未来变更）
- 支持分布式多 GPU 索引（仅单 GPU）
- 完全替换 JSON 存储（两者可以共存）
- 从头构建自定义向量数据库
- 支持非 CUDA 加速器（ROCm、Metal、仅 CPU 回退）

## 决策

### 决策：使用 cuVS 而不是 FAISS
**理由：**
- cuVS 专为 NVIDIA GPU 构建，与 RAPIDS/cuML 集成
- 层次聚类将受益于 GPU 加速（cuML 提供基于 GPU 的链接算法）
- FAISS 需要 CPU<->GPU 传输；cuVS 将数据保留在 GPU 上
- 项目已经使用 CUDA（PyTorch），因此 CUDA 依赖是可接受的

**考虑的替代方案：**
- FAISS：更成熟但以 CPU 为中心，需要手动 GPU 传输
- Milvus/Qdrant：对于研究用例过度设计（需要服务器、REST API）
- ChromaDB：更高级别但添加了不必要的抽象
- 纯 NumPy：已经证明对于大型数据集太慢

### 决策：支持多种索引类型（IVF-Flat、IVF-PQ、CAGRA）
**理由：**
- IVF-Flat：良好的准确性，中等速度，适合中等数据集（<100K 向量）
- IVF-PQ：压缩索引，更低内存，快速搜索，轻微精度损失
- CAGRA：最先进的基于图的索引，最适合大型数据集（>100K）
- 作为配置参数公开，以便用户可以调整速度/精度权衡

**默认值：** IVF-Flat（平衡选项，更易配置）

### 决策：保留 JSON 导出与 cuVS 并行
**理由：**
- 对现有分析脚本的向后兼容性
- 人类可读格式对调试有用
- 最小开销（并行写入）
- 如果需要，用户可以禁用 JSON

### 决策：存储元数据（文件名、文件夹名）与向量
**理由：**
- 聚类结果需要可追溯到源文件
- cuVS 原生不支持元数据；将其存储为按向量 ID 键控的单独字典
- 将元数据序列化为 JSON 与 cuVS 索引一起存储

## 风险 / 权衡

### 风险：CUDA 依赖限制可移植性
- **影响：** 无法在仅 CPU 的机器或非 NVIDIA GPU 上运行
- **缓解：** 保留 JSON 存储作为回退；突出记录 GPU 要求；在启动时检测缺失的 CUDA

### 风险：cuVS API 稳定性（早期阶段库）
- **影响：** 未来 cuVS 版本中的破坏性变更
- **缓解：** 在 requirements.txt 中固定特定 cuVS 版本；每次升级时测试

### 风险：索引损坏或不兼容
- **影响：** cuVS 更新后无法加载保存的索引
- **缓解：** 在索引中存储 cuVS 版本元数据；从 JSON 备份添加重建脚本

### 权衡：大型索引的内存使用
- **影响：** 单 GPU 系统上的 GPU 内存限制（A6000/4090 约 24GB）
- **缓解：** 对大型数据集使用 PQ 压缩；记录每种索引类型的内存要求

### 权衡：大型索引的构建时间
- **影响：** 超过 100K 向量的初始索引构建可能需要几分钟
- **缓解：** 对新嵌入进行增量更新；缓存已构建的索引；显示进度条

## 迁移计划

### 阶段 1：在不干扰现有工作流的情况下添加 cuVS（此次变更）
1. 将 `VectorStore` 实现为独立类
2. 在配置中添加选择性标志 `use_vector_store: false`（默认禁用）
3. 保持所有现有 JSON 工作流不变
4. 在数据子集上测试（仅 Chart 类别）

### 阶段 2：验证后默认启用
1. 将默认值更改为 `use_vector_store: true`
2. 在现有 JSON 嵌入上运行迁移脚本
3. 验证搜索结果与基于 NumPy 的相似性匹配

### 阶段 3：聚类集成（未来变更）
1. 使用 cuVS + cuML 实现层次聚类
2. 为树状图/聚类添加可视化工具
3. 使用聚类嵌入创建分析笔记本

### 回滚计划
- 如果 cuVS 证明不稳定：通过配置禁用，回退到 JSON
- 如果 GPU 内存不足：使用较小的批处理大小或 PQ 压缩
- 如果构建时间过长：离线预构建索引，作为制品分发

## 实现说明

### 索引配置建议
```yaml
# 小型数据集（<10K 向量）
index_type: ivf_flat
nlist: 100
nprobe: 10

# 中型数据集（10K-100K 向量）
index_type: ivf_flat
nlist: 1000
nprobe: 50

# 大型数据集（>100K 向量）
index_type: cagra
graph_degree: 64
intermediate_graph_degree: 128
```

### 向量存储 API 设计
```python
class VectorStore:
    def __init__(self, index_path, config):
        """初始化或加载现有索引"""
    
    def add_vectors(self, vectors, ids, metadata):
        """添加带有 ID 和元数据的向量"""
    
    def search(self, query_vector, k=10):
        """返回 k 个最近邻"""
    
    def batch_search(self, query_vectors, k=10):
        """批量最近邻搜索"""
    
    def get_all_vectors(self):
        """检索所有向量（用于聚类）"""
    
    def save(self):
        """将索引持久化到磁盘"""
```

## 待解决问题

1. **我们应该支持增量索引更新还是每次运行时重建？**
   - 建议：两者都支持；对于小批量增量，对于批量操作重建

2. **默认距离度量应该是什么？**
   - 建议：L2（欧几里得）以匹配典型的嵌入相似性语义
   - 替代：如果嵌入已归一化，则使用内积

3. **我们应该默认使用 PQ 压缩嵌入吗？**
   - 建议：默认不压缩（保留完整精度）；为大型数据集添加 PQ 选项

4. **如何处理向量维度验证？**
   - 建议：在索引元数据中存储维度；在插入时如果不匹配则引发错误
