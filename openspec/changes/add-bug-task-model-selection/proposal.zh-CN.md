# 变更提案：基于聚类的 Bug 修复任务建模选择

## 为什么
不同类型的 bug 可能更适合不同的任务建模形式（例如“生成完整的修复后代码”vs“输出 Search/Replace 编辑”，或不同的 prompt 组织方式）。但 bug 的“类型/特征”往往是内生的，仅凭肉眼很难从工件中稳定判断。

我们希望构建一套系统化、数据驱动的方法，用于：
- 基于 bug 的多类工件（report、test info、buggy code、（可选）混淆/派生 code）将 bug 聚成可解释的类别；
- 对每个类别采样代表点；
- 利用 `ppl/result/` 中已有的灰盒信号（例如 O/IO PPL）为每个类别选择更合适的任务建模；
- 在簇级别与全局级别评估该“聚类→路由/选择”的有效性。

## 变更内容
- 增加多视角的 bug 表征流水线（Report / Test Info / Buggy Code / 混淆后的 Buggy Code / 混合 Code）。
- 增加凝聚式（自底向上）层次聚类 runner，输出可解释的 merge tree，并支持多个切分粒度（cut levels）。
- 增加每个簇的代表点选择（多样性采样），用于后续决策与人工检查。
- 增加 `ppl/result/` 的结果读取与聚合，并基于代表点的 PPL 为每个簇分配“优先任务建模”。
- 增加评估与报告（簇级与整体指标），用于衡量该路由/选择策略的效果。

## 影响
- **受影响的规范：** 新能力 `bug-task-model-selection`
- **受影响的代码（预期）：**
  - 将在一个全新的、可自包含的目录中实现新增代码，以避免修改现有模块；并按 `src/` 与 `data/` 清晰分层组织（以 opt-in 脚本形式运行）。
- **破坏性变更：** 无（新流水线为可选启用）
