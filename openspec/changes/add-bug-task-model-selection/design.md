## Context
This change introduces a cluster-guided routing pipeline to select an appropriate task modeling formulation per bug.

Existing components in this repo:
- `prompt_list/<slug>/...`: per-bug artifacts (e.g. `query.txt`, `FAILED_TEST.txt`, `ERROR_MESSAGE.txt`, `BUGGY_CODE.txt`, etc.)
- `embedding/`: embedding generation + vector store (optional GPU)
- `embedding/hierarchical_clustering.py`: current hierarchical k-means clustering (center-based)
- `dpp/kdpp_sampling.py`: greedy DPP-based representative selection over clustering outputs
- `ppl/` + `ppl/result/`: PPL evaluation outputs for different task modelings (e.g. `d4j_gen`, `d4j_edit`), including per-case JSON results
- `fix/cluster_model_selector.py`: baseline that chooses GEN vs SR per cluster based on representative *repair success* counts

The proposed pipeline shifts the selection signal from “repair success” to “grey-box” PPL metrics and extends clustering to be:
- agglomerative (bottom-up) for better interpretability (merge tree / dendrogram), and
- multi-view (report/test/code/obfuscated/mixed) to capture different latent bug factors.

## Goals / Non-Goals

### Goals
- Provide an explainable multi-level clustering of bugs (and/or bug views) using agglomerative hierarchical clustering.
- Support multiple “views” of bug artifacts:
  - report-like (current `query.txt`)
  - test info (failed test code)
  - error info (stacktrace / exception)
  - buggy code
  - derived views: obfuscated buggy code, mixed/combined code variants
- Select representative points per cluster (coverage + diversity) to enable manual inspection and cluster-level decision making.
- Ingest `ppl/result/` outputs for at least two task modelings and select a preferred task modeling per cluster using representatives.
- Produce evaluation reports comparing routing strategies and baselines using PPL-based metrics.

### Non-Goals
- Replacing existing repair pipelines (GEN/SR) or the `ppl/` scoring implementation.
- Training new models.
- Guaranteeing perfect correlation between PPL and repair success (PPL is treated as a proxy signal).

## Proposed Pipeline (High Level)
1. **Multi-view item construction**: for each bug `slug`, build one or more items `(slug, view)`.
2. **Embedding**: compute embeddings per item and persist to a vector store with rich metadata (slug/view/source path).
3. **Agglomerative hierarchical clustering**: cluster items within a chosen view (or a bug-level aggregated vector) and export:
   - merge tree (children + distances)
   - multiple cut levels (e.g. k=10/20/50)
4. **Representative selection**: for each cut level, select per-cluster representatives (1+ items) with reproducible seed.
5. **PPL ingestion**: load PPL results for the same slugs from `ppl/result/` for multiple task modelings.
6. **Cluster-level task-model selection**: decide the preferred task modeling per cluster using representatives’ PPL.
7. **Evaluation & reporting**: compute cluster-level and overall metrics, and generate a human-readable report.

## Key Design Decisions

### View schema
- Base views come from files in `prompt_list/<slug>/`.
- Derived views (obfuscated/mixed) are generated by deterministic transforms.

Proposed canonical view names:
- `report` (from `query.txt`)
- `error` (from `ERROR_MESSAGE.txt` or extracted from `query.txt`)
- `test` (from `FAILED_TEST.txt`)
- `buggy_code` (from `BUGGY_CODE.txt`)
- `buggy_code_obfuscated` (derived)
- `buggy_code_mixed` (derived; e.g. concatenation or shuffling policy)

### Stable IDs and metadata
Every embedded item should be uniquely addressable and traceable:
- `item_id`: `"{slug}__{view}"` (or equivalent stable scheme)
- required metadata: `slug`, `view`, `source_file`, `tokens`, optional `transform_config`

### Agglomerative clustering implementation
- Use `sklearn.cluster.AgglomerativeClustering` with `compute_distances=True`.
- Default distance/linkage:
  - `metric = cosine`
  - `linkage = average`
- Export merge tree via `children_` + `distances_` arrays.

### Multi-level clustering outputs
- Provide multiple cut levels:
  - `k`-cuts: e.g. `k ∈ {10, 20, 50}`
  - optionally: `distance_threshold` cuts
- Each cut should export:
  - cluster list (cluster_id, size)
  - member item ids
  - cluster “center” for downstream sampling (centroid of member vectors) and/or medoid id

### Representative selection
Goal: sample representatives per cluster while keeping interpretability and reproducibility.

Two compatible approaches:
- **Reuse current greedy DPP sampler** by exporting clusters with computed centroids as `center`.
- If DPP reuse is not feasible for a specific view, fall back to:
  - per-cluster medoid as the first representative
  - farthest-first traversal inside the cluster for additional reps

### PPL ingestion
`ppl/result/` contains per-case JSON outputs with differing directory layouts:
- flat: `.../<run_ts>/<slug>/result.json`
- per-sample: `.../<run_ts>/<slug>/<sample_idx>/result.json`

The ingestor should:
- discover runs and tasks (this change explicitly targets `d4j_gen` and `d4j_edit`)
- extract at least `ppl` and `avg_nll` (and optionally `ppl_io` / `io_ppl` if present)
- aggregate per (slug, task, metric) over samples using a configurable reducer (default: median)
- emit both O and IO metrics when available, so that routing/evaluation can be performed under each metric definition

### Cluster-level task-model selection rule
Initial heuristic (configurable):
- For each cluster, compute the aggregated PPL metric over representatives for each task model.
- Choose the task model with **lower** representative PPL.
- Tie-breakers and fallbacks:
  - if missing data for one model, choose the other
  - if missing both, choose a default (configurable)

### Evaluation
Report at least:
- per cluster: rep PPL distributions for each task model, chosen model, and delta
- overall: routed PPL vs baselines:
  - always GEN
  - always SR
  - oracle per bug (min PPL across models)

## Risks / Trade-offs
- Obfuscation quality: naive obfuscation may distort semantics; robust parsing may be expensive.
- PPL as proxy: lower PPL may not always correlate with repair success.
- Data join complexity: run timestamps and directory layouts vary; missing/partial results must be handled.
- Compatibility: `ppl/` runtime uses Python >= 3.13; selection code should only *read* outputs and remain Python 3.10 compatible.

## Migration Plan
- Keep existing clustering (hierarchical k-means) and selection baselines intact.
- Add the new pipeline as opt-in scripts and outputs under a new capability.
- Provide a report that compares the new PPL-based routing against existing success-based routing (optional).

## Open Questions
- Whether clustering is performed at bug level (one vector per bug) or view level (multiple items per bug), and how to reconcile multi-view decisions.

## Decisions (Clarifications)
- The routing/selection scope for this change is limited to exactly two task modelings: `d4j_gen` vs `d4j_edit`.
- If both O and IO PPL metrics are available, the pipeline SHALL support both, produce routed-by-cluster results for each metric definition, and compare which metric yields better downstream outcomes.
- Across per-sample results, the default reducer is median (configurable to mean).
